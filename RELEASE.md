# Releases

pg_arca ships as two products with one version number:

| Artifact | For | Contents |
|---|---|---|
| `pg-arca-console-<v>-linux-x64.tar.gz` | the console host | bundled server (`server.mjs`), web UI (`dist/`), the agent bundle the console serves, Node.js runtime, `install-console.sh`, `Dockerfile` |
| `pg-arca-agent-<v>.tar.gz` | database and worker hosts without access to the console's download URL | the agent; `./install-agent.sh` installs it offline |
| `pg-arca-agent_<v>_all.deb` / `pg-arca-agent-<v>-1.noarch.rpm` | fleets managed with apt/dnf repositories | the agent in `/usr/share/pg-arca-agent`; a package upgrade upgrades the agent in service |
| `SHA256SUMS`, `BUILDINFO` | everyone | checksums; version, commit, Node.js runtime, agent fingerprint, test result |

The console always serves the agent of its own release (`/agent/install.sh`, `/agent/pg-arca-agent.tar.gz`), and the agent packages contain the same code (the build checks the fingerprint). An agent of another release is shown as outdated in the console, with its upgrade command.

Installation and operations: [INSTALL.md](INSTALL.md).

## Versioning

- One version for console and agent, in the `VERSION` file. `tools/release/set-version.sh X.Y.Z[-rc.N]` writes it to `VERSION`, `package.json` and the agent; `tests/server/version.test.ts` fails if they disagree.
- Semantic versioning. Pre-releases: `-rc.N` (release candidate). In package managers the pre-release sorts before the final release (`1.0.0~rc.1` in deb/rpm).
- The console shows its version under the product name and in `/api/health`; agents report theirs to the console.

## Building a release

```
npm ci
tools/release/set-version.sh 1.0.0-rc.1       # if not set already; commit it
tools/release/build.sh                         # out/release-<v>/
```

The build stops on: a version mismatch, failing tests (`npm test`: server, UI logic and agent unit tests), a failing UI build, a packaged console that does not start or does not serve the UI and the agent (smoke test), a Node.js runtime with a wrong checksum, an agent package whose code differs from the one the console serves, a high or critical `npm audit` advisory in the production dependencies (the result is recorded as `npm_audit=` in `BUILDINFO`; `unavailable` when the registry cannot be reached). A build from a working tree with uncommitted changes is marked `-dirty` in `BUILDINFO` and is not a release build.

## Release gate

A release candidate (`-rc.N`) is published when the build passes and the lab runs (`tools/lab/`) are green on the supported PostgreSQL versions that are already verified. The final release (GA) needs all of the following, each recorded in `HANDOFF.md` with the date and the evidence:

| Gate | State on 1.0.0-rc.1 |
|---|---|
| Version matrix 14, 15, 16, 17, 18 green with the full suites (`tools/lab/matrix.sh`), `VERIFIED` in `pgcompat.py` updated | 15, 16, 17 PASS; 14 and 18 to rerun after fixes |
| Real network storage as backup destination: NFS and SMB, including loss of the share during a backup | not done |
| Console install, upgrade from the previous release and rollback on clean VMs (RHEL family and Debian/Ubuntu) | **passed** 15/10 on Debian 12, Rocky 9, Ubuntu 24.04 (`tools/lab/release-test.sh`, 0 failures, build 73a50f2): install, upgrade, automatic rollback of a broken release, `--rollback`, uninstall/reinstall, purge |
| Agent upgrade through `.deb`/`.rpm` on a registered node, and removal refused while WAL archiving is active | package install + registration with a private CA, upgrade by reinstall (service restarted), removal: **passed** 15/10 on the three distributions (worker host); removal refused while archiving is active: to run on a database node |
| Security review: authentication and sessions, RBAC on every route, agent enrollment and tokens, command execution on nodes, TLS, systemd hardening, dependency audit | partly: RBAC sweep of every mounted route (`rbac.test.ts`), login back-off, sessions and API tokens tested, `npm audit` in the build (clean), `systemd-analyze security` printed by the release test; agent (command execution on nodes, path handling, secrets, enrollment: 8 findings) and console (authentication, RBAC, secrets at rest, input handling: 11 findings, one critical) reviewed once each by a separate reviewer on 15/10, all findings fixed in rc.1 — see below; still to be reviewed by someone outside the project; the agent's inbound API (off by default) stays plain HTTP on loopback; `/metrics` also accepts the token as `?token=` (proxy logs) |
| Console state backup and restore procedure tested (`install-console.sh --backup-state`, `--restore-state` on another host) | **passed** 15/10 (backup, purge, fresh install, restore, users and state back) on the three distributions |
| Installation and administration guide reviewed by someone who did not write it | first version in INSTALL.md |
| No open defect classified as data loss or wrong restore | no open one known |

## Release candidates

### 1.0.0-rc.1

First packaged release. Changes since the development builds:
- One version for console and agent (`VERSION`); shown in the UI and in `/api/health`.
- Console: native TLS (`PG_ARCA_TLS_CERT`/`PG_ARCA_TLS_KEY`, reload with SIGHUP), listen address (`PG_ARCA_LISTEN`), paths resolved from the install directory instead of the working directory.
- Console installer for systemd hosts: system user, hardened unit, settings file kept across upgrades, state backup before every upgrade, automatic rollback when the new release does not start, `--rollback`, `--backup-state`, `--restore-state`, `--uninstall`.
- Container image recipe for the console.
- Agent packages: offline tarball, `.deb`, `.rpm`; the installer has a no-package mode for them (`PG_ARCA_NO_PKG=1`).
- The whole interface, server messages and agent messages in English (guard tests on all three).

Fixed during the rc.1 test round (15/10):
- Recovery point measured from where PostgreSQL writes, not from the clock alone: an idle cluster with archive_timeout no longer reports hours of "data at risk" (only a completed segment still waiting for the archiver keeps the long bound).
- WAL quarantine: the agent classifies each refused copy against the current timeline history. Copies a failover leaves behind (the old primary's tail of a timeline it left, partial segments, sibling branches, ancestor history files) are informational, with "File away the failover leftovers"; only copies on the shared history are an urgent split-brain signal. A copy is quarantined once per content (also on NFS) and not again after review.
- A cluster whose agents have been silent for more than three days is a warning that names the ways out (restart the agent, or detach the cluster) instead of a permanent "critical"; a failed operation always carries a message.
- Console simplicity: one "is it protected?" sentence per cluster (list, header), one date format everywhere, one verdict box in the restore wizard, destructive restore choices labelled with their impact, quieter activity notifications, honest geo readiness, full mobile navigation.
- Backups taken on a standby: the console asks the primary to switch its WAL segment when the backup reaches the WAL phase; an archive that receives nothing is diagnosed as not shared within a minute (`PGA-WAL-021`, with the remedy) instead of a blind two-minute timeout; the Backup page warns before starting when the cluster has no shared destination.
- Patroni member names: a node whose hostname differs from its Patroni member name was listed twice and switchover/failover/restart/reinit failed with "not a member of this cluster"; the agent now reports its member name and every Patroni action uses it.
- Access (HBA): new cluster access matrix, every node → every node, for the replication user and the superuser, with one click to add the missing explicit rules (through the DCS on Patroni, per node otherwise).
- Geo-redundancy: a site that comes back after a failover is fenced (demoted) at its first sign of life, before Patroni there can promote it; the dead WAL branch of a timeline two servers used can be retired from the Backup tab (nothing is deleted).
- Backup server with a folder: the directory check shows every problem with its remedy and, when it passes, the exact NFS export, mount line and destination to set.
- Dialogs no longer steal the cursor while typing (polling pages re-focused the first field; copy/paste lost its selection).
- Cluster header badge agrees with the health findings.
- Backup copy and restore extraction run with a sliding window over the worker threads instead of batches with a barrier.
- Repository format 2: backup chunks are stored in pack files (`cas/packs/*.pack` + `.idx`, up to 256 MB each) instead of one file per 64 KB chunk; a 100 GB database is a few hundred files instead of 1.6 million. Repositories written before stay readable (their files are deduplicated against and garbage-collected as before; new chunks go to packs) and are marked `format: 2` on first use. **A development build older than this change cannot read a repository written by rc.1.** Measured locally: +30 % on a full backup to a local disk; the gain on NFS/SMB (where every file costs a round trip) is expected to be much larger and is not measured yet.
- PostgreSQL 17+: incremental backups driven by WAL summaries (`summarize_wal = on`): relation files the summaries do not mention are not read at all, mentioned ones only at the changed chunks; falls back to the page scan whenever the summaries do not cover the range, and a sample of the "unchanged" files is scanned in full as a check. Unit-tested with a simulated server; the real-PostgreSQL-17 test runs in the lab matrix (not run yet at the time of writing).
- Offsite copy of the repository and the WAL archive on S3-compatible object storage (Status → Nodes → Offsite copy): mirrored in the background by the agent of the node that holds the repository; "Download what is missing here" rebuilds a lost backup storage from the copy; console finding when the copy is failing or more than 6 hours behind. Verified against a simulated S3, the AWS SigV4 test vector and a real S3-compatible server with signature checking (SeaweedFS, 15/10: mirror, deletion after the grace, rehydrate into an empty repository, hostile object names, pagination; a wrong secret is refused); not yet against AWS S3 itself or Ceph, and not yet driven from the console on the lab.
- Asynchronous WAL archiving, off by default (Status → Nodes → Paths and discovery → "Asynchronous WAL archiving"): for WAL rates the synchronous archive_command cannot sustain; the spool is shown in the console and counted in the recovery point, and the trade-off (a segment in the spool is lost with the host) is stated where it is switched on.
- Recovery objectives on the Backup tab: the recovery point (what is not in the WAL archive yet) and the recovery time (from the last drill, scaled to today's size), with their state. A backup policy can declare the objectives the business committed to (RPO and RTO in minutes; "Critical production" = 15 min / 4 h, "Standard production" = 1 h / 8 h): the tab shows measured vs objective, and a finding tells when the measured recovery point is above it (with `archive_timeout = N s` to set when the parameter alone exceeds it), when `archive_timeout` is not set so the objective is not guaranteed, or when the estimated recovery time is above it. `pg_arca_cluster_rpo_target_seconds` / `rto_target_seconds` on `/metrics`.
- Backup policies: retention also in days of recoverability (chains younger than N days are kept whatever the count); read rate limit (MB/s) for scheduled backups, so that a backup never saturates production storage; hours for heavy work (full backups and verifications only between HH and HH of the console's clock, incrementals whenever due; a cluster without any full is protected at once).
- Sign-in through LDAP / Active Directory (Users page → Directory sign-in): simple bind over ldap:// + StartTLS or ldaps:// with certificate verification, user search with a service account or a DN template, groups → console roles (highest wins) with a default role or refusal, bind password stored encrypted, a test button, every sign-in audited. Local accounts always win; a directory account disabled in the console stays blocked. Implemented without dependencies (BER encoding of bind/search); verified against a simulated directory and ldaps with a private CA, not yet against a real Active Directory.
- API tokens for automation (Users page: bearer tokens with their own role and expiry, revocable, every action audited as `token:<label>`).
- Installer and packages, found by the release test on fresh Debian 12 / Rocky 9 / Ubuntu 24.04 containers: the first install exited 2 at its last step, the automatic rollback after a broken release was refused by systemd's start limit (and lost the `--rollback` record), the agent scripts were not executable in the packages; `--restore-state` added. Second cycle: the agent service died at start with `PermissionError` when `PG_ARCA_TLS_CA` pointed at a root-only file (`/root/console.crt`, the console's own `tls/` directory) — the installer now copies the CA to `/etc/pg-arca/console-ca.pem`, readable by the agent's user, and points the config at the copy (also on upgrades). Console state snapshots, deep verify reading every chunk once, restore reading adjacent chunks in one call, parallel dump in database restores, archiver-backlog and no-zstd findings, Prometheus RPO/RTO metrics, "Running on this cluster" strip refreshed at once.
- Security review of the console (independent reviewer, 15/10) with its fixes. **One critical defect in the development builds, fixed here: the directory (LDAP) settings routes under `/api/auth/` were reachable without a session** — anyone on the network could point the console at their own directory with `defaultRole: admin` and sign in as administrator; now only the sign-in routes are public and the RBAC sweep covers `/api/auth/*`. Also: credentials inside operation parameters (offsite keys, the password of a delivery address) are encrypted in the state and never returned by the API (the agent gets them at hand-off); a node that already reports cannot have its identity taken over by a new enrollment (409), and a node approved into one environment that reports another environment's cluster key is not merged into that cluster (audited, left to the operator); a malformed answer from a directory no longer crashes the console; the sign-in answer no longer leaks directory details (they go to the audit log) and the attempt is counted before the directory is asked, with a per-account cap whatever the source address; pg_hba rules that open the server to the network without a password (`trust`) or with a clear-text one (`password`) are for administrators only and need four-eyes where approvals are on; an API token cannot approve the request of the administrator who created it; webhook URLs are encrypted at rest; agent progress and discovery payloads are bounded; `constructor`/`toString` are not operation types.
- Review of the backup engine for data loss and wrong restores (independent reviewer, 15/10), six confirmed defects, all fixed with regression tests: **a backup could deduplicate against a pack that a concurrent garbage collection (an `expire` of another stanza sharing the repository: geo pair, second cluster, another node) deleted meanwhile, leaving a COMPLETE set whose restore fails with `PGA-REPO-014`** — now backups and migrations hold a repository-wide shared lock (`cas/gc.lock`) and the collector skips its pass while one runs, and a chunk whose pack vanished is stored again instead of trusted; retention in days kept only the fulls younger than N days and deleted the chain covering the start of the window (with weekly fulls up to a week of the promised history was lost, WAL included) — the newest full older than the cutoff is kept too; a delta restore over a copy newer than the target kept that copy's pages where the backup had none (all-zero ranges are not stored), leaving tuples from the future that no checksum reports — uncovered ranges are zeroed now; after a change of destination the WAL between the switch and the first new full could be expired although sets of the previous location are restorable; WAL summaries with two version directories in one tablespace (left by pg_upgrade) could skip the wrong files — now scanned in full when in doubt; two archivers racing with different contents could both report success and leave a segment whose metadata do not match it — the object is published write-once first and only the winner writes its metadata.
- Security review of the agent (command execution, paths, secrets, enrollment) with its fixes: an operation can no longer choose the directory the agent runs binaries from (`ephemeral` and `into.bindir` are refused by the console and ignored by the agent); the offsite download refuses object names that resolve outside the repository / archive or onto an existing file; the agent refuses the same dangerous settings the console refuses (`archive_command`, `*_preload_libraries`, Patroni `callbacks`, `standby_cluster`, …), so a tampered console or a daemon-token holder gets no command execution; an explicit delivery address for a restore (`into`) is for administrators only, and a site can be demoted only under a registered peer site; an enrollment token can no longer replace the secret of a node that already reports; offsite credentials live in `agent.secrets.json` (0600); a finding when an agent talks to the console over plain http:// or without verifying its certificate.
- Found on the lab's geo pair on real NFS (15/10 evening): on NFS a retransmitted MKDIR answered "File exists" for the backup set directory the agent had just created, failing every second scheduled backup — new set directories are now claimed with an exclusive-create marker (exactly-once on NFS) and empty leftovers are removed by retention; after a geo failover the new primary's archiver stayed blocked on a divergent copy of an old-timeline segment that its own history never reads (15 hours without archiving) — such a copy is now acknowledged and kept in quarantine, while a divergence on shared history still stops archiving for a human to decide.
- Offsite "Download what is missing here" no longer brings back what retention or garbage collection removed on purpose (found driving it from the console on the lab: 8 GB of WAL came back); after a real loss of the storage everything is downloaded as before. The "WAL archiving is failing" finding names the way out when a divergent copy blocks the archiver (retire the dead branch of timeline N) — verified on the lab, where it unblocked a site after 15 hours. Recovery objectives on the Backup tab refresh as soon as a policy changes.
- Geo-redundancy: a site counts as rejoined only when it really follows the new primary (streaming, on a timeline not ahead of it); a false "rejoined" is reopened and a standby site that is ahead of the primary is rebuilt from it (found on the lab: one sample of a WAL receiver that died at once had closed the case, and the site stayed unprotected).
- Geo rejoin of a site that had promoted itself while cut off: the timelines it abandoned are set aside in the WAL archive before it is rebuilt (wal_retire_branch with abandoned=true, also available by hand): otherwise every member recovering from the shared archive tries to follow the dead timeline and restarts in a loop (found on the lab).
- Review of the restore engine (independent reviewer, 16/10), fixed with regression tests: a whole-server restore no longer starts when the tablespace safety check could not run (WAL unreadable and the live server not answering) or when the pre-flight itself failed — before, it only warned and a replayed CREATE TABLESPACE could remove a live tablespace's files; a delta restore empties the previous copy's `pg_wal` (its own timeline history made PostgreSQL follow the copy's timeline and replay the copy's writes) and its `tablespace_map`, and cleans inside the tablespaces; an incremental backup that ends past the point where the recovery leaves its timeline (a lagging standby promoted) is no longer used — the earlier sets plus the archived WAL reach the target; an incremental ending within two seconds of a time target is not chosen as the base (its end could lie after the target); an in-place server restore refuses a data directory that is a mount point before stopping anything, puts production back up if a rename fails, checks the space for the not yet archived WAL before the stop, and gives a root-run agent's files to the data directory's owner; an encrypted WAL object whose writer died before writing its metadata is recognised (and its metadata written) instead of blocking archiving as a "split-brain"; recovery files are synced before the copy is declared ready and `postgresql.auto.conf` is rewritten atomically; the DROP DATABASE search follows the timeline history; the standbys to rebuild after an in-place restore are named.
